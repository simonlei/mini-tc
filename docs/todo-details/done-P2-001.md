- [x] **修：`BatchRenameDialog` 序号输入框清空时 `v-model.number` 得 `""` 被当成 0 而非回落到默认** — `renameRules.js:141-148`。
  **已修（2026-10-16）**。🚨 **TODO 原文的因果被实测推翻，这是本条最重要的产出**：原文说清空「步长」会让所有行拿到同一序号，「被 `buildRenamePlan` 判重全部标红，整批无法执行」。实测（`buildRenamePlan` 真实签名是 `(items, existing, rules)`，`existing` 要 **Set** 不是数组）结果是 **`ok=3 errors=0`** ——
  `a.txt/b.txt/c.txt` 算出的目标是 `a_1/b_1/c_1`，**三者互不相同，判重压根不触发**。所以这不是「整批被拦下」的可用性问题，而是**静默写坏**：整批顺利执行、名字全改错、界面上没有任何红字或报错。清空「起始」同理，静默从 0 开始编号。
  - **根因**：`v-model.number` 绑在 `<input type="number">` 上，清空时得到的是**空串**（Vue 的 `looseToNumber("")` = `parseFloat("") || ""`）而不是 0；旧守卫 `Number.isFinite(+v) ? +v : 1` 对此完全失明 —— `+""` 就是 `0`，`0` 是有限数，**那条 `: 1` 兜底永远不可能触发**。
  - **修法**：抽 `seqNumber(value, fallback)`，三个字段统一走它。判据是「**空**」不是「假值」：`null` / `undefined` / `""` / 纯空白 → 回落；而 **`0` 必须照用**（输入框是 `min="0"`，从 0 开始是合法需求）—— 这条是「用 `if (!v)` 一行写完」会引入的回归。
  - 顺带 `parseInt` → **`Number`**：旧代码 `parseInt(rules.seqPad, 10) || 0` 会把 `"3abc"` 解析成 3。
  - **测试 `scripts/rename-rules-check.mjs` 102 → 140 例**：清空回落（起始 / 步长 / 补零 / 全空白 / null / undefined / 非数字）、**合法 `0` 必须被尊重**（含显式 `step: 0` 冻结编号这个对照组）、钳位（`99` → 十位零，`-5` → 0）、**端到端过 `buildRenamePlan`** 断言整批三个名字，以及一条**对照臂**证明「冻结编号确实过得了判重」—— 没有它，上面那条「判重不触发」的结论就没有被钉住。
  - **变异测试 `scripts/seq-number-mutation.mjs`（新，已挂 `npm test`）**：8 个变异**全部被抓**，含「原样退回旧守卫」「删掉空串判断」「改用假值判断」「parseInt 换回 Number」「回落 0 而非调用方的默认值」。按 METHODOLOGY 纪律打印 `anchor found: N` 并断言 `N === 1`（替换失败也会 exit 0，否则「0 FAIL」无法区分「断言瞎」与「变异没进去」），跑完比对源文件字节一致并还原。
  - ⚠️ **写断言时我自己错了 3 条**（`0004` 应为 `04`、序号期望算错、`seqPad: 99` 期望写成 `"1"` 而钳位到 10 才是对的）。按纪律逐条查了是测试错还是代码错 —— **三条全是测试错，代码是对的**。其中「`seqPad` 钳位」那条查完才发现：改对之后的期望值 `"0000000001"` 恰恰**就是钳位生效的证据**，差点被当成 bug 去改代码。
  - 另补一组**静态断言**（三个序号字段确实都走 `seqNumber` + 旧陷阱 `+rules.seq*` 不再出现），防「改实现不改调用点」；并**实测验证它有分辨力**：把 `seqPad` 改回内联 `parseInt` 后确实 FAILED，否则属于 METHODOLOGY 警告的「恒绿断言」。
  - `npm run check` exit 0（15 个套件全绿）。**待用户双击 `dev.sh` 实测**：批量改名对话框清空「起始」应从 1 开始、清空「步长」应逐行递增，且红色提示消失。
