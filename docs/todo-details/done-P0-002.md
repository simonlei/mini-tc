- [x] **修复：合并移动时用户选的「不覆盖」被忽略，且跳过的文件照样被删源** — `lib.rs:2052/2065/2078/2092`。三处连环出错：① `move_items` 的跨卷分支判据是 `copy_failed = !copy_errors.is_empty()`，而 `copy_all` 遇到冲突且用户选「不覆盖」时走 `*skipped += 1; continue`（`1889/1898/1861`）**不进 errors** → `errors` 为空即删源，目标位置还是旧文件，用户看到「移动成功」而源已消失。② 合并移动分支 `copy_all(&app, &merge_move, dest_path, true, ...)`（`2078`）把 `overwrite` **硬编码为 true**，注释只论证了「目录 vs 目录」这一种冲突，递归到叶子文件冲突时 `plan_overwrite`（`1706-1710`）照样返回 `Replace` → `remove_recursive(dest)` 把目标文件永久删掉换成源文件。③ `2092` 的注释写着「若还有残留 remove 会失败、于是保留源、更安全」，但 `remove_recursive`（`1587`）走 `path.is_dir() → fs::remove_dir_all`，会**愉快地删掉残留内容、不失败** —— 注释的推理是错的，残留项等于直接丢失。修法：① 「可否删源」的判据改成 `errors.is_empty() && skipped == 0`，`skipped` 由 `copy_all` 单独返回而非只累加进 `&mut`；② `plan_overwrite` 增加「目录合并只对 dir-vs-dir 生效、对叶子冲突仍尊重用户 `overwrite`」的第三种策略，别用 `overwrite=true` 一刀切；③ `merge_move` 删除源前逐项校验源侧已空，只删空壳目录，残留项如实列出交给用户。**先补测试再改**：这三条全是「单看每处都正确、组合起来才丢数据」，而 `plan_overwrite` / `move_items` / `same_path` / `path_key` / `is_ancestor_or_same` 目前**零测试覆盖**，反倒纯函数的 `glob_match` 有 7 个用例、`window_state::resolve` 有 9 个。
  - ✅ **已实现（2026-10-11）**。三条同源，**病根是一处语义耦合而非三个独立 bug**：`copy_all` 的 `overwrite: bool` 一个参数同时表达「叶子冲突要不要替换」和「目录冲突要不要合并」。合并移动必须合并（`rename` 到非空目录不可能），所以只能传 `true`，而那个 `true` 又顺着递归漏到每个叶子冲突上，把用户选的「不覆盖」顶掉了 —— 三个症状全部由这一处派生。
    - **① 拆参数**：`plan_overwrite(src, dest, overwrite_leaves, merge_dirs)` 两个独立维度。目录 vs 目录**只**由 `merge_dirs` 决定（合并移动恒传 `true`，不再受 overwrite 影响）；叶子冲突**只**由 `overwrite_leaves` 决定（恒为用户选择）。合并移动传 `(overwrite, true)`。
    - **② 删源判据从「黑名单」改成「白名单」**：原逻辑「`errors` 为空 → 全删」漏掉了 skip 这种**静默**失败（不产生错误信息，调用方无从察觉）。`copy_all` 新增 `moved_sources: &mut Vec<PathBuf>`，只回报**整棵树完整无冲突搬走**的源，跨卷与合并移动两个分支都只删名单内的源；未搬完的如实上报「`X` 未完全搬走/未完全合并，已保留源文件/源目录」。**判据用白名单而非黑名单**：黑名单要穷举所有失败原因，漏一个就是数据丢失。
    - **③ 归属判定抽成纯函数** `plan_task_action(src, dest, overwrite_leaves, merge_dirs) -> (OverwriteAction, bool /*taints*/, Option<String>)`。任务循环用它把 skip/失败**归属回所属的顶层源**（`ranges: Vec<(start, end, PathBuf)>` 记录每个源的任务下标区间，单调 cursor O(n) 归属），tainted 的源不进 `moved_sources`。抽成纯函数是因为 `copy_all` 需要 `tauri::AppHandle` 发进度事件、单测构造不出来 —— **即项目约定的「纯逻辑把 IO 以参数注入」**（与 `renameRunner` 注入 `move(from,to)` 同思路）。`OverwriteAction` 补 `#[derive(Debug, Clone, Copy, PartialEq, Eq)]` 供断言输出。
    - **④ 两个边界**：a) `collect_copy_tasks` 对「既不是文件也不是目录」的源（如死符号链接）产出 **0 个 task**，若不处理会被当成「搬完了」而删源 → 空 range 直接标 tainted；b) `move_items:2021` 的 `plan_overwrite(...)?` 会把单源错误升级成命令级 `Err`、**丢弃已完成的若干项**且与 `copy_items` 的返回契约不一致 → 改为收集进 `errors` 后 `continue`。
    - **测试**：新增 `mod overwrite_tests` 共 9 例（`cargo test --lib overwrite_tests` 9 passed / 0 failed）。覆盖 `plan_overwrite` 决策表（目标不存在 4 组 / 目录冲突 4 组 / 叶子冲突+类型不符 4 组）、`plan_task_action` 的「合并+不覆盖 → Skip 且 taint」「合并+覆盖 → Replace 且不 taint」「源消失 → Err」「干净树 → 不 taint」「自覆盖 → Skip 且 taint」，以及 `remove_recursive_would_delete_leftovers`（把「`remove_dir_all` 会删残留」这个**危险前提本身**钉成测试，防止有人改回「源还在就删」的朴素写法）。
    - **测试有效性已验证**：把 `plan_overwrite` 的目录分支回退成旧的耦合写法（`if merge_dirs && overwrite_leaves`）重跑，`plan_directory_conflict_follows_merge_dirs_only` **确实失败**，恢复后全绿。另一次返工：第一版测试在测试体内**复刻了一遍生产逻辑**（手工调 `collect_copy_tasks` + 手工判 taint），看着端到端、其实测的是测试自己的副本，已重写为直接调 `plan_task_action`。**判据：测试调的必须是生产代码实际走的路径；全绿的测试和没测试一样，必须验证它能抓住回退**。
    - 前端零改动（`CopyResult{errors, skipped}` 字段名与语义未变，只多几条更准确的错误文案）。`cargo check` / `cargo fmt --check` 均 exit 0。**待用户双击 `dev.bat` 实测**（4 个场景：合并移动选「否」→ 目标文件内容不变 + 源目录保留；选「是」→ 内容替换 + 源目录移除；同卷移动正常；目标在源内部仍被拒绝）。
