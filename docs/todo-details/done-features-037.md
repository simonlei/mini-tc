- [x] **Ctrl+Z 回滚「最近一次删除到回收站」（可撤销删除）** — 当前 `Delete`（`list.delete` → `FilePanel.onDelete` → 后端 `delete_to_trash`）把文件送进回收站后就彻底没了交互出口：minitc 没有撤销栈、没有「回收站」面板、也不能一键还原。用户希望按 `Ctrl+Z` 能把**最近一次送入回收站的文件**恢复回原位；**一次删多个时按一次 Ctrl+Z 多个一起恢复**；**`Shift+Delete`（彻底删除）不可回滚**（这是用户明确口径，不要给「永久删除」也加撤销，那会误导成可恢复）。目标行为对齐 Total Commander / 资源管理器的「撤销删除」。需处理：
  - **① 后端恢复能力（已有现成 crate API，不要自己解析 `$RECYCLE.BIN`）**：`trash` 5.2.6 提供 `trash::os_limited::list()`（返回 `Vec<TrashItem>`，Windows/Linux 才有，macOS 无此模块）和 `os_limited::restore_all(items)`。`TrashItem` 自带 `id` 与 `original_path()`（`name` 另存原文件名），足够定位。**跨平台要条件编译**：`macos` 分支只能降级为「不支持撤销删除」toast，不能编译不过。
  - **② 🚨 最大的坑：`trash::delete(path)` 不返回 `TrashItem`**（当前 `delete_to_trash` 就只返回 `Result<(), DeleteError>`），所以「删了哪些回收站条目」必须自己建立对应关系。可行做法是**删除前 `list()` 记 id 快照、删除后再 `list()` 取差集** → 差集即本批。⚠️ 三个已知歧义要处理：① 两次删除之间有别的进程/另一个 mini-tc 实例动过回收站 → 差集里混入别人的项，需按 `original_path()` 与本次实际删掉的路径集合**求交集**再兜底；② 同一路径被删两次（恢复过一次又删）→ `original_path()` 相同，用「最新 time / 快照中未出现过的 id」挑；③ `list()` 要遍历并解析整个回收站的 `$I` 文件，回收站里有几万个条目时会明显慢 → 实测量级后考虑只按名字/路径做定向匹配，或把快照限制在时间窗口内。
  - **③ 撤销栈的粒度 = 「一次操作」而非「一个文件」**：`onDelete`（`FilePanel.vue:1354`）循环删 N 项，应在循环**开始前**记快照、循环**结束后**记一条完整批次（含 N 个 `TrashItem`），Ctrl+Z 一次吐一整批。⚠️ 现有 `onDelete` 里已知的「循环内多次 await 后重读 `activeTab.value.path`」（见 P1 审查条目）会让批次元数据（源目录、tab）不可靠，**做本条时应顺手按审查建议在入口处快照 `(tabId, dir, list)`**。用户口径目前只要求「最近一次」，故**先只保留一层**（栈深 1）即可；若做深栈，每层仍是一批。
  - **④ 冲突处理（`restore_all` 的错误分支）**：`Error::RestoreCollision { path, remaining_items }` = 原位置已有同名文件；`Error::RestoreTwins` = 同一批里 `original_path` 重复（多选里不可能，但要防）。前者必须提示用户「原位置已被占用」，提供「改名恢复 / 跳过」两条路（改名沿用 `BatchRenameDialog` 的 `validateName` 规则），不能静默失败也不能默认覆盖——**默认覆盖等于用撤销键做数据破坏**。冲突项成功恢复的仍应留在回收站之外（已成功的就是移走了），失败的要如实列出残留路径。
  - **⑤ 提权删除（`delete_with_admin`）不可回滚**：`delete_with_admin` 走的是提权 `PowerShell Remove-Item`，文件根本没进回收站 → 天然不在撤销栈里。UI 上别把它算进「最近一次删除」（`onDelete` 尾部那段 `adminLaunched` 分支不要 push 批次）。
  - **⑥ 恢复后刷新谁**：恢复的源目录**不一定**是当前活动面板（可能刚 Ctrl+Z 前的操作发生在另一栏、或期间切了目录）。需按批次元数据里的 `(tabId, dir)` 通知对应面板刷新（`FilePanel` 已有 `refresh()`，虚拟搜索 tab 不适用）；恢复目标若正是当前活动目录，则按 `paths.js` 的 `normDir` 比对后再 `selectName` 选中刚回来的项（对齐删除后自动选下一条的既有手感）。
  - **⑦ 快捷键与输入框**：`shortcuts.js` 注册 `edit.undo`（scope `global`，默认 `Ctrl+Z`），走既有 COMMANDS 注册表、可被用户改绑；⚠️ 必须 `isTypingTarget` 守卫（地址栏/过滤框/重命名输入框内的 Ctrl+Z 是原生文本撤销，**不要**抢）；可选再加 `edit.redo`（`Ctrl+Y` / `Ctrl+Shift+Z`），但用户没要求，栈深 1 时也无从重做，先不做。
  - **⑧ 反馈**：`Ctrl+Z` 成功恢复 N 项 → toast「已从回收站恢复 N 项」；无可撤销批次（栈空 / 上次是永久删除）→ 明确 info toast「没有可撤销的删除」，不要静默无反应。
  - **⑨ 与既有 `list.delete` 的关系**：`list.delete` 与 `list.deletePermanent`（`shortcuts.js:103/106`）都不变；撤销**只**认进回收站的那条路径。彻底删除的项**不进栈**，因此不会出现「Ctrl+Z 把 Shift+Delete 删掉的东西拉回来」这种用户明确不要的行为。
  - 实现（后端 `src-tauri/src/lib.rs`，零新增依赖）：① **复用 crate API，不碰 `$RECYCLE.BIN`** —— 用 `trash::os_limited::list()` / `restore_all()`，按 `os_limited` 的 cfg 条件编译整套撤销命令（macOS 无此模块，落到空实现 = 「没有可撤销的删除」，而非编译失败）。② **批次括号拆成两个命令**：`begin_trash_delete()` 回收站 id 快照 → 前端删完整批 → `commit_trash_delete(before, deleted)` 差集 + 求交集 + 记栈。快照**按批取不按文件取**（`list()` 要枚举整个回收站）。③ **栈深 1**（`static TRASH_UNDO: Mutex<Option<TrashUndoBatch>>`），刻意不做通用撤销栈。④ **三个歧义都处理了**，且抽成纯函数 `select_new_trash_items(before, after, deleted)` 以便单测：差集滤掉「删除前就在」的；与 `deleted` 求 `path_key` 交集滤掉「删除期间别人塞进去的」（顺带兜住快照失败导致 `before` 为空的最坏情况）；同 `original_path` 保留 `time_deleted` 最大的那条。⑤ **冲突绝不覆盖**：`undo_trash_peek()` 非消费地报告哪些项原位置被占用（这一步必须在消费之前，因为要等用户回答），前端弹「改名恢复 / 跳过」，改名走 `undo_trash_delete(renames)` 传 `HashMap<原路径, 新名>`；后端改写 `TrashItem::name` 后恢复（两个平台后端都是「移到 `original_parent` 下、改用 `name`」，所以改这一个字段就是改名恢复）。`Error::RestoreCollision` 一律进 `skipped`，不碰目标。
  - 实现（前端）：`shortcuts.js` 注册 `edit.undoDelete`（scope `global`，`Ctrl+Z`，可改绑）；`App.vue:onUndoDelete` 编排 —— peek → 无批次则 info toast「没有可撤销的删除」→ 有冲突则 `showConfirm`（「改名恢复」为 primary，自动名用 `pickRestorableName` 生成 `名称 (N).扩展名`，**复用 `renameRules.js` 的 `splitName` / `validateName`** 而不是另造一套命名规则）→ 执行 → **只刷新「当前目录命中恢复目标」的面板**（恢复源目录未必是活动面板，用 `normDir` 比对 `parentDirOf`）→ 在命中的活动面板里 `nextTick(selectName)` 选中刚回来的第一个 → 双栏 `refreshDrives()` → 按 restored / skipped / errors 分别 toast。⚠️ 额外加了一条模态闸门 `if (confirmDialog.value.visible) return`：撤销冲突框打开时再按 `Ctrl+Z` 会弹第二个框并覆写 `confirmResolve`，第一次那个 Promise 永不 resolve、这次撤销静默消失（就是审查里那条已知漏洞，本功能新增的弹框路径正好会踩到它）。
  - **顺带修 `onDelete` 的 await 后重读**（审查 P1 条目点名的那个）：现在入口处快照 `(tab, tabId, dir)`，循环内只用快照值写 `entries` / `updateDirSizes` / `tab.search.hits`，不再读可能已经切走的 `activeTab`。
  - **验证**：`cargo test --lib` **36 passed**（新增 6 条 `undo_batch_*`）、`cargo fmt --check` 干净、`vite build` exit 0（主 bundle 259.78 kB，改动前 257.26 kB）、`npm run check` 全绿（导入 28 文件 + 102 + 22 断言）。⚠️ **新测试的有效性是实测过的，不是看着绿就算**：先回退交集守卫 → 「他人条目」与「快照失败」两条失败；再回退取最新逻辑 → **第一版测试竟然全绿**（因为两条目恰好把新的排在前面，「先到先得」蒙对了），改成**对称断言两种顺序**后才抓住。教训与上次同款：`list()` 不保证顺序，任何依赖「先到先得」的测试都必须两种顺序都断言，否则它测的是运气。
