- [ ] **修复：CLI 解压/压缩路径没有任何超时 → 工具卡在密码提示上时调用线程永久阻塞** — ⚠️ **2026-10-19 取证：机制成立，但「三个调用点」实为 2 个，且「7z 等密码」这一具体机制不成立。**
  - ✅ 成立部分：当前压缩工具相关的 `cmd.output()` **无超时点只有 2 处** —— `extract_archive`（`4286-4288`）与 `add_to_archive`（`4420-4422`），均无 deadline / `try_wait` 轮询 / `kill`，与 GUI 分支形成完全不对称。GUI 分支的超时循环在 `4259-4274`（200ms 轮询 + `GUI_WAIT_LIMIT` 600s，`4136-4139`，注释明说「must never stall a batch extraction forever」），且**只在 `wait == Some(true)` 时启用**。另 3 处 `Command::new`（`3189` xdg-open、`3893` where.exe、`3898` which）是工具发现用的短命令，不在本条范围。
  - 🚨 **「`7z x 加密包` 会等待密码」不成立**：Rust 的 `Command::output()` 按文档会把 stdin 设为 **null**（子进程读 stdin 立刻拿到 EOF），7z 的控制台密码提示应当立即报错退出而非挂起。**但结论不变** —— `winrar` 语法（`4219-4227`/`4367-4375`）调的是 `WinRAR.exe` 本体，它在需要交互时弹的是**模态 GUI 对话框**，该窗口不关闭则进程不退出，`cmd.output()` 无限等待，这条阻塞路径在结构上成立；即便不涉及交互，大包解压的耗时本身也没有上界，而 GUI 分支作者认为需要 600s 安全阀的理由同样适用于 CLI 分支。
  - 修法：两个 `cmd.output()` 统一走已有的等待循环（`4259-4274`）+ kill，需配合新增 `Stdio` 处理。
